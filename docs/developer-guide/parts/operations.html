Identity, authorization and security boundaries

Keep separates the question “Who is this person?” from “What may this person do here?” Keep checks a person's company password with one LDAP bind against Active Directory and reads people and groups from ADAPI, the company directory REST API. The Product API authorizes their requests using a valid application session, trusted directory evidence and current Keep grants. A successful login alone does not give access to every tenant, and hiding a frontend button never replaces a server-side permission check.

Follow a human request across the boundary

  1. A signed-out browser opens Keep's /sign-in page. The user enters a company username and password, and the page posts them as JSON to POST /auth/login.
  2. The API checks the same origin, the username and a non-empty password, then performs one ldap3 simple bind with the configured bind format and asks WhoAmI who is bound. The password is used for that bind only; it is never stored, logged or forwarded.
  3. The API reads the person's own ADAPI row. A disabled account gets the same refusal as a wrong password. A new or changed person is published through the ordinary publisher, then the API creates an opaque application session with a 24-hour absolute limit and no idle timeout.
  4. For each protected request, the API combines that session with the accepted directory checkpoint and current grants. Mutations recheck authorization through their commit boundary; live subscriptions enforce the same tenant access.

The application origin serves the UI, /api and /auth. Environment configuration supplies the LDAP host, port, encryption setting and bind format, the ADAPI address and its ClientId secret, and the super-admin group. The browser's protected cookie, same-origin checks and CSRF protection are part of the contract. Sign-out ends the session in Keep only. Do not place credentials in browser storage, log a password, or add a test login route to simplify a local test.

Directory evidence and tenant roles

Active Directory remains authoritative for people and nested teams. Keep identifies users and groups by their lowercase samAccountName from ADAPI; display names and email addresses are labels, not identities. Keep grants combine direct and team membership using the highest role: view, edit, then admin. Assignment gives responsibility, not permission. Global is a fixed tenant with its own universal eligible-user edit policy; tenant administration and global administration remain distinct.

Current scope uses explicit trusted publication. There is no continuously polling directory worker and no current five-minute propagation promise. Complete bootstrap or manual publication supplies trusted identity evidence. Existing eligible users may continue from the last trusted checkpoint without an age cutoff, while known revocations, current grant changes, logout and session expiry still apply. Sign-in never reads groups: memberships come only from a refresh or a save on pick, never from a guess at sign-in.

Why partial identity refreshes cannot replace the trusted view

A directory timeout is not proof that a person left every team. Publication separates complete positive evidence from independently verified negative facts and prevents older observations overwriting newer ones. Unknown or incomplete evidence can block a new grant or admission without stripping existing valid access. Read keep.identity.publication for the transaction and generation checks before changing this behavior.

Isolated development replaces Active Directory and ADAPI with a local OpenLDAP for the bind and a mock ADAPI for people and groups, using the same adapi keys and normal publication. That exception removes the company directory dependency; it does not qualify company AD or ADAPI integration or create a login bypass. Session expiry and restore gates still apply.

Tenant isolation belongs in every data path

Authorization selects the accessible tenant before listing, searching or counting. Nested resource IDs, selectors, cursors and subscription targets must belong to that tenant. An inaccessible resource uses the non-disclosing unavailable response; insufficient write permission on a visible resource is a different error.

PostgreSQL row-level security adds a database boundary for the API role. The shared transaction helper sets transaction-local keep.tenant_id; tenant policies check it for reads and writes. Use the existing helper and the appropriate runtime identity. Worker privileges are deliberately different because workers process multiple tenants, so domain queries and composite tenant references remain essential. A passing test under a privileged database login is not evidence that API-role isolation works.

For an authorization change, cover at least the permitted action, an insufficient role, a cross-tenant reference and permission loss during a concurrent command. Include counts, errors and live hints in the review: a hidden name or count can still disclose another tenant's data.

Operate the system without losing its guarantees

Start diagnosis by identifying which guarantee failed: admission, authoritative processing, automatic decisions, search visibility or browser refresh. A healthy pod proves only its readiness contract. It does not prove that a received alert reached SQL, became searchable or appeared in a browser. Trace one synthetic delivery across those boundaries before increasing traffic.

Know what success means at each stage

A successful ingestion 202 means Kafka acknowledged admission. It does not mean PostgreSQL processing, correlation or indexing completed. The processor commits canonical alert state and immutable replay proof in PostgreSQL, then publishes changed events together with received-input offsets in a Kafka transaction. Those are two coordinated commits, not a distributed transaction spanning PostgreSQL and Kafka.

If the Kafka transaction fails after the SQL commit, replay uses the recorded proof rather than applying the business change twice. Preserve its event identity, bytes and ordering. Correlation consumes tenant-ordered changes; indexing consumes independently and reconciles against PostgreSQL. Elasticsearch is rebuildable current-alert search data. Redis carries refresh hints; PostgreSQL reconciliation repairs missing hints.

Apply one migration chain before dependent writers

keep-migrations owns the complete ordered PostgreSQL chain and the dedicated migration image. REV-38 wraps immutable SQL in Alembic while preserving the checksum ledger. Runtime services never migrate on startup. Migration SQL, revision wrappers and checksums must agree; numbering gaps are intentional historical facts.

  1. Identify the exact release combination and inspect pending migrations, their prerequisites and the supported starting schema. Preserve applied bytes and add a forward migration for corrections.
  2. Complete required drains and fences. The current 0048–0052 changes require the stopped-writer migration window; older cutover and stopped-scheduler prerequisites still apply when those migrations are pending.
  3. Run the dedicated migration Job using its separate migration identity before dependent writers. Require successful completion and verified ledgers before startup.
  4. Start only the compatible application combination and execute the relevant replay, authorization, maintenance and search checks. An available older image does not establish rollback compatibility.
Read-only migration inspection and legacy adoption

From the keep-migrations checkout, the documented commands below inspect packaged history without connecting to PostgreSQL. They are navigation aids, not an executed migration.

poetry run alembic history
poetry run alembic heads

A legacy database with only schema_migrations is adopted only after its checksums form an exact prefix of the known chain. Pending changes and adoption share a transaction and advisory lock. The existing ledger and alembic_version must agree. Investigate an integrity error; never manually stamp a database, edit old checksums or drop a ledger to make it pass. There is no automatic downgrade or database-rewind rollback.

Cutover, rebuild and restore are separate operations

Kafka protocol cutover fences old admission, drains accepted work using compatible consumers, stops legacy workers, captures topic boundaries and initializes the new consumer groups under explicit stopped-workload prerequisites. Never mix incompatible generations or reset groups on a live installation. A command flag declaring writers stopped does not stop them; establish the real state first.

Fresh search activation verifies an empty authority/index and supplied Elasticsearch capabilities before recording the initial binding. Populated data requires the fenced rebuild procedure: preserve the current authority, copy and catch up under the selected index epoch, then switch through the verified alias protocol. Do not run empty-install bootstrap against a populated deployment.

A database restore has broader obligations. Independently protected credential, deletion and replay evidence must survive the database recovery point. Keep affected paths fenced until current deployment authority, tenant order, clocks, offsets and search epochs are reconciled. Restoring SQL availability alone cannot prove that a revoked key stays revoked or that retired content remains inaccessible.

When a Kafka offset is below the retained low watermark

Kafka can expire acknowledged but unprocessed inputs. Preserve the lost interval and stop unsafe source or correlation recovery. The service owner establishes available retained data; a reviewed reset records loss and establishes fresh correlation boundaries. Do not silently choose earliest/latest or claim PostgreSQL can recreate source inputs it never received. Search can rebuild committed SQL state; that is a narrower guarantee. A producer resubmission is a new delivery.

Release readiness is evidence about a specific combination

Keep spans independent repositories but remains a coordinated system release. Matching branch names do not establish compatibility. Record repository revisions, package/contract versions, image digests, migration checksums, configuration, design revision and executed evidence. Local editable packages are useful development overrides; release locks must resolve immutable artifacts without sibling checkout assumptions.

Prepare a concrete deployment candidate

  1. Identify changed producers, consumers, shared packages, schema and UI. Publish prerequisite artifacts and update dependent pins and the delivery manifest together.
  2. Build the selected images and record digests. Validate generated contracts, affected tests and actual-version integration requirements. Distinguish controlled API fixtures from real browser/identity evidence.
  3. Obtain real environment bindings: endpoints, versions, trust, identity references, namespace/topic/index allocations, service capabilities and owner contacts. Keep secrets outside reports and source control.
  4. Prepare the compatible rollout and rollback procedures, including drains, migration Job and startup order. Execute only within the environment's authorization and isolation boundaries.
  5. Run initialization and end-to-end synthetic checks before load qualification. Measure the full workload and retained-data growth, then record limitations instead of converting partial success into readiness.

The private OpenShift bundle is an isolated-test handoff. Its example allocations, external service placeholders and test identities on a test OpenLDAP and mock ADAPI are inputs for a supplied environment, not company defaults. Namespace separation alone does not isolate shared Kafka topic names. Keep owns application behavior and its sign-in configuration; dedicated teams own Active Directory, ADAPI, PostgreSQL, Elasticsearch, Kafka, Redis, OpenShift, Kong and Grafana infrastructure, including capacity, retention, backups and service recovery.

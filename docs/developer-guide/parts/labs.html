11 · Put it into practice

Practise explaining the boundaries

Use these exercises with an onboarding partner. The guide's simulators change only illustrative data in this page. The commands in earlier chapters are separate instructions; buttons here never connect to a Keep environment.

Three source-reading exercises

Exercise 1 · Trace one alert from sender to screen

Choose a synthetic v2 alert with one application/key pair. In the repository explorer, locate admission, source processing, domain lifecycle, indexing and frontend API code. Draw where the delivery UUID, input coordinate, alert ID and occurrence are introduced or used. Mark both commits and the search visibility boundary.

Done when: you can explain why 202 does not guarantee an alert is visible; why a restart cannot reapply the SQL mutation; why a new client submission is not the original replay; and why detail can be newer than a Feed result. Use the pipeline lab's crash scenario to check your account.

Exercise 2 · Find the code your test actually imports

Prepare the documented editable workspace. From delivery, inspect one shared module's origin without contacting a service:

# Working directory: keep-delivery
.venv/Scripts/python.exe -c "import keep.alerts.lifecycle as m; print(m.__file__)"

Compare that path with the sibling checkout you intend to edit. Inspect delivery's lock and the repository inventory. Explain which path changes after a pinned install and why running a dependency sync can undo an editable override.

Done when: your test evidence identifies the interpreter, actual imported source, relevant commit and local modifications. Do not edit installed package copies as a fix.

Exercise 3 · Investigate a stale view without changing authority

In the pipeline lab choose Elasticsearch unavailable. Compare sender response, PostgreSQL state, committed input offset and search status. Then select the Redis failure scenario. Explain why the two outages have different symptoms.

In source, locate the indexer's reconciliation/visibility checks and the API's live generation reconciliation. Write the evidence you would collect from a real isolated reproduction before restarting anything.

Done when: your diagnosis separates search failure from hint loss, preserves unavailable/stale UI states, and never proposes rebuilding PostgreSQL from search results.

12 · Keep learning

Vocabulary and source map

TermMeaning in Keep
TenantThe product authorization and data scope. Global is fixed; an operator's owning tenant is immutable.
OperatorAn ingestion configuration/credential identity, not a human role or a standalone worker.
Logical alert / occurrenceA continuing application/key record / one firing cycle within that record.
Delivery / input coordinateAn admitted envelope with an internal UUID / its original Kafka topic, partition and offset.
Command ID / expected revisionIdentity used to recover a human command without duplicate execution / the concurrency precondition for its target.
Replay proofDurable immutable evidence of source application, including the original changed-event result needed after a crash.
Projection / watermarkRebuildable search representation / verified progress boundary for refresh-visible search state.
Fence / epochA guard preventing unsafe work / a generation that distinguishes valid current work from older state.
CELCommon Expression Language used for typed filters and conditions. Allowed fields and semantics depend on the product context.
RLS / SSEPostgreSQL row-level security / server-sent events used for scoped browser invalidation hints.
Editable dependencyA local development override importing a sibling checkout; it is not an immutable release artifact.

Read requirements before older examples

This guide is an explanatory onboarding aid. The linked specifications, current decisions and repository instructions remain authoritative. In particular, current worker scope supersedes retained scheduler/polling algorithms in older documents.

  • System specification and current worker scope: start here for scope.
  • Architecture index and design register: follow responsibilities and approved decisions.
  • Verification plan: behavior that must be proved.
  • Workspace setup, local execution and Kafka operations: use the actual procedures.
  • Implementation status and delivery readiness: distinguish implemented features, executed checks and open gates.
  • Daily-user guide: learn the user workflows your code supports.

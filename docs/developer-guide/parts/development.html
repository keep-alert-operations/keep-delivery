Prepare a local development workspace

Develop from the parent directory containing the eleven independent Appchi repositories. Delivery supplies the coordinated Python environment, workspace inventory and local launchers; each repository still owns its source, Git history and checks. The commands below are instructions for a developer to run when their prerequisites are satisfied. They are not a record of checks executed while preparing this guide.

1. Establish the tools and checkout state

The documented prerequisites are Python 3.13, Poetry 2.3.1, Node.js 22.17 or newer, npm and Git. Private repository access must already work through your approved Git credential helper. Docker and the documented local identity/TLS setup are additional prerequisites for the full local stack; they are not required merely to read source. Check versions without printing credentials:

# Working directory: workspace root
python --version
poetry --version
node --version
npm --version
git --version
git -C appchi-delivery rev-parse --show-toplevel
git -C appchi-delivery status --short --branch
git -C appchi-delivery diff --stat
git -C appchi-delivery diff --cached --stat

Read the root AGENTS.md, then the affected repository's instructions and README. Repeat the Git inspection for every repository you will change, including untracked files. Preserve existing work. Matching branch names do not establish compatible revisions, and an existing directory is not proof of an independent checkout.

2. Bootstrap and install the coordinated environment

For a new workspace, first obtain the delivery checkout through the organization's approved repository access. Run the following from appchi-delivery, located directly under the intended workspace root:

# Working directory: appchi-delivery
python scripts/workspace.py bootstrap
python scripts/workspace.py install --editable
.\scripts\dev.ps1 -Action Check
python scripts/workspace.py inventory --output .local/workspace-inventory.json

Bootstrap clones missing siblings at the manifest's immutable commits. It preserves existing repositories and their branches rather than resetting them. New sibling checkouts can therefore be detached at a pinned commit; create a task branch before making changes there. Bootstrap also installs the canonical workspace instructions. If a different root instruction file and an earlier backup both exist, it stops for reconciliation instead of overwriting them.

Installation first resolves the committed delivery lock, then replaces installed Python packages with editable local sources and runs the frontend's locked npm installation. It does not start services or apply migrations. dev.ps1 -Action Check checks Python/imports and frontend dependency/runtime availability; without its explicit configuration flags, it does not validate service connectivity or readiness.

The inventory records each checkout's commit, dirty state and manifest match, plus migration checksums. Keep this with your test evidence. It describes the files you have, not a qualified release.

After preparing editable dependencies, use delivery's .venv/Scripts/python.exe directly for coordinated Python checks. A later dependency synchronization can restore pinned packages, so do not assume an earlier editable install still describes the active environment. If dependency metadata changes, resolve and review the appropriate lock changes before reinstalling; --no-deps editable overrides do not resolve new dependencies for you. Never commit machine-specific editable paths.

Portable commands and an individual Python repository

The workspace guide documents .venv/bin/python instead of .venv/Scripts/python.exe on Linux/macOS. The Python workspace script provides bootstrap, install, inventory and test actions there too. The PowerShell runtime launchers describe the Windows local environment; do not assume every local-stack step has a portable equivalent.

# Working directory: the affected Python repository
poetry check --lock
poetry sync --all-extras
poetry run ruff check src tests
poetry run pytest tests/unit -q
poetry build --format wheel

Use the repository's actual test layout and workflow. This sequence is the common package CI pattern, not a substitute for its integration tests.

3. Choose the right local execution path

Inspect the existing environment before starting anything. Delivery coordinates one Compose project and managed local application processes. A second processor or launcher pointed at the same stores can compete with the first. Historical startup notes show past evidence; they do not establish that services are running now.

# Working directory: appchi-delivery
.\scripts\local-runtime.ps1 -Action Status

Follow the local runtime guide and local identity setup before Start. Establish the intended isolated stores, matching local credentials, TLS trust and required cutover/evidence gates. Start is consequential local setup: it can prepare credentials, launch dependencies and apply migrations before writers. Keep existing volumes and their matching .local material.

# Working directory: appchi-delivery
# Only after the local-runtime prerequisites and existing processes are checked.
.\scripts\local-runtime.ps1 -Action Start
# Later, for an intentional managed application reload:
.\scripts\local-runtime.ps1 -Action Start -Restart
# When finished with this managed stack:
.\scripts\local-runtime.ps1 -Action Stop

Stop preserves volumes. Do not remove them as a startup repair. The documented browser entry is https://localhost:3443. Local startup publishes trusted identities once; subsequent local identity changes use the documented explicit refresh, not a directory poller. Correlation has a separately bound preview gate; a successful API start does not prove it is enabled.

Make a change without breaking its neighbors

Begin with behavior and ownership

Read the system design, current worker scope and the supplement governing the behavior. Define the observable acceptance condition before coding: the triggering input, the expected state and what must remain unchanged. Resolve a source/specification conflict rather than quietly choosing whichever is easier. Current user decisions can supersede older examples and retained implementation algorithms.

Coordinated development uses the explicit editable environment; copying shared code into consumers creates competing authorities.

A small first change: strengthen an alert ownership regression

  1. Read alert operations section 17 and the frontend UI design. The invariant is that assigning a firing alert displays Acknowledged; removing assignment displays Firing. Suppression is separate.
  2. Inspect src/lib/alert-status.ts, src/components/alert-table.tsx, src/components/alerts.tsx and the existing synthetic scenarios in tests/redesign.spec.ts. Identify a genuinely missing assertion or edge case; do not duplicate existing coverage.
  3. Check the frontend branch and local changes. Reuse the relevant task branch, or create a suitable codex/ branch from the verified starting revision. Add one focused regression using existing fixture conventions.
  4. Run the targeted browser file in the isolated synthetic test environment below. If it exposes a defect, implement the smallest correction consistent with the invariant and rerun that scenario.
  5. Review the rendered result and diff. Run affected frontend checks, then describe precisely whether you added coverage, changed behavior, or both. This exercise does not authorize a production release.
# Working directory: appchi-frontend
# Existing installed Chrome, prepared npm dependencies, test port available.
# Ensure APPCHI_REAL_BROWSER_DATABASE_ADMIN_URL is not set for this run.
$env:PLAYWRIGHT_CHANNEL = 'chrome'

npm test -- tests/redesign.spec.ts

Preserve and restore any pre-existing environment values instead of discarding them. The ordinary Playwright configuration uses port 3100 and can reuse an existing server; check what owns that port before the run. A separate build directory avoids overwriting the ordinary server's output, but does not provide a separate port by itself.

Regenerate contracts in dependency order

For an HTTP change, update the owning Product API or Ingestion API source first. The delivery generator imports those installed applications and writes separate producer OpenAPI documents plus the aggregate into contracts. It also generates event schemas from the shared event models. Use the editable environment when the intended producers are local modified sources:

# Working directory: appchi-delivery
.venv/Scripts/python.exe qualification/generate_contracts.py
.venv/Scripts/python.exe qualification/check_contracts.py
.venv/Scripts/python.exe qualification/verify_boundaries.py
git -C ../appchi-contracts diff -- schemas

Review changed schemas as compatibility changes. Never patch only a generated file. Commit the contract authority and advance affected immutable dependency references and locks in dependency order. Frontend generation reads its installed @appchi/contracts package, not the sibling schemas directory. After updating its package reference and lock through the normal package workflow:

# Working directory: appchi-frontend
npm ci
npm run generate
git diff -- src/lib/generated.ts

Complete affected consumer tests before advancing delivery's workspace manifest and lock. Record prerequisite commits, merge order and the tested combination. Several repository PRs do not form an atomic release; compatibility must cover the supported mixed state or the documented coordinated cutover.

When a change needs PostgreSQL schema work

Use only appchi-migrations. Inspect the current chain before selecting a new number:

# Working directory: appchi-migrations; locked dependencies already installed
poetry run alembic history
poetry run alembic heads

These commands do not connect to PostgreSQL. Preserve published SQL bytes, checksums and numbering gaps; corrections use a new forward migration and one linear chain. Follow the migration README for the wrapper, SQL file and new checksum. Runtime services never migrate on startup. Migration execution needs its dedicated identity before dependent writers and any documented offline prerequisites; a new application image alone cannot make an incompatible rollback safe.

Prove the changed behavior

Choose checks from the acceptance condition and affected boundaries. A narrow UI copy change needs less verification than a lock-order, schema or pipeline change. Finish required checks; broaden when a failure, new scope or unresolved concern justifies it. Serialize heavy native CEL suites, frontend builds and browser suites on this workstation so resource contention does not become a false failure.

Separate synthetic browser coverage from real integration

The ordinary browser suite intercepts API traffic with synthetic fixtures. It is useful for rendering, navigation, forms, conflicts and visible permission states. It does not establish real authorization, database transactions, search consistency, Kafka processing or company service compatibility. Inspect the relevant desktop/narrow behavior and actual user interaction, not just a successful build.

The opt-in real browser fixture uses an actual HTTPS frontend, API and a disposable PostgreSQL database. It requires APPCHI_REAL_BROWSER_DATABASE_ADMIN_URL for an isolated cluster whose identity can create and drop test databases, prepared delivery dependencies and a supported browser. Supply that binding through the local secret/configuration process before running:

# Working directory: appchi-delivery
# Prerequisite: explicitly supplied isolated disposable PostgreSQL admin binding.
.\scripts\verify.ps1 -Suite BrowserReal -BrowserChannel chrome
# Separate integration suite; requires APPCHI_TEST_DATABASE_URL.
.\scripts\verify.ps1 -Suite Database

The Database suite applies migrations and writes synthetic records to its configured isolated test database. Real browser evidence still does not qualify real Keycloak sign-in or the complete Kafka/search pipeline. The local-runtime browser configuration exercises a different, explicitly opt-in environment; follow its runbook instead of interchanging these tests.

Understand CI and finish with honest evidence

The common Python workflow performs locked install, Ruff, owned unit tests and wheel build. Delivery additionally bootstraps the pinned workspace and checks contracts, boundaries and documentation. Frontend CI regenerates its client, fails on generated-file drift, then checks formatting, types and build. Its current workflow does not run Playwright, so a green frontend CI result alone is not browser verification.

Private dependency workflows require the configured read-only repository credential. A credential preflight failure means subsequent checks did not run. Refer to the current workspace setup instructions for access arrangements; never copy token values into commands, code or reports.

For handoff, record affected repositories and exact revisions, local modifications or editable overrides, commands and working directories, outcomes, screenshots where relevant, and skipped checks with their missing prerequisite. Distinguish an assertion failure from an unavailable service. Keep runtime evidence in delivery and normative behavior in design. Passing tests on one local combination does not qualify another set of dependency pins, production capacity or deployment readiness.

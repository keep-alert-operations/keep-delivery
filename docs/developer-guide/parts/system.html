Team engineering handbook · 11 October 2026

Understand Keep.
Trace it. Change it safely.

An interactive onboarding guide for the developers who build and operate Keep. Follow an alert from admission to the browser, explore where code belongs, and practise the failure boundaries before making your first change.

Begin with the boundaries. PostgreSQL owns business state. Kafka carries the alert pipeline. Elasticsearch is a rebuildable search projection. Redis carries hints. Splitting repositories did not split the database or make releases independent.

What you should be able to do

  1. Explain what an accepted alert means and identify the two independent commits that follow.
  2. Locate a behavior in the correct repository, then identify its producer, consumers, schema and tests.
  3. Prepare an isolated local workspace without replacing existing data or quietly testing pinned code instead of your edits.
  4. Preserve tenant isolation, command identity, expected revisions, lock order and replay proof in a change.
  5. Diagnose a stale view or blocked pipeline using the responsible authority and its progress evidence.
  6. Describe what your verification proves and what still needs integration or release qualification.

The labs are simplified learning models with synthetic data. They do not contact Keep, execute the displayed commands, or constitute integration tests. The written chapters remain available without JavaScript; use an enabled browser for the interactive parts.

Suggested first-week learning sequence
  1. Orient: read the product model and architecture; explain the repository split back to a teammate.
  2. Trace: use the pipeline lab, then read the actual admission and source-consumer functions it links.
  3. Run: follow local development in an approved isolated environment and record your exact revision combination.
  4. Change: make one bounded improvement, identify affected consumers, and run its meaningful checks.
  5. Review: walk through an uncertain command and a projection outage with your onboarding partner. Finish the knowledge checks and discuss any wrong answers.

This is a suggested sequence, not an estimate or a release gate. Completion checkboxes track your reading, not technical qualification.

01 · Structure

One system, eleven repositories

Keep is a multi-tenant alert management product. Monitoring sources update logical alerts; people take responsibility, leave notes and coordinate incidents. Shared CEL queries power feeds, presets and count dashboards. Rules can correlate fresh alert evidence into incidents, and maintenance can suppress qualifying activity without dropping it.

The deployed application uses Python/FastAPI services and a Next.js/TypeScript frontend on OpenShift. Domain and contract packages are libraries, not services. Most runtime repositories contribute modules to the shared Python keep namespace, but each module has one owner. An import path alone therefore does not tell you which checkout to edit.

Dependency direction is a design constraint

Services consume pinned contract and domain packages. Domain may depend on contracts; neither imports a service route or entrypoint. Delivery can assemble all services for local and system tooling, but production services must never import delivery. Ingestion may use stateless shared helpers; it must not acquire Keep PostgreSQL, Elasticsearch, Redis or human-identity adapter dependencies.

The repositories share one transactional schema. Do not turn a SQL invariant into a distributed protocol simply because two callers live in different repositories. Conversely, do not reach into a sibling checkout as a runtime shortcut: use documented editable installs during development and immutable dependency artifacts for release.

02 · Follow one delivery

Accepted, applied and searchable are different states

There are two HTTP surfaces. The Ingestion API accepts machine-generated alerts. The Product API serves authenticated people, management commands and searches. A source payload cannot choose a tenant by inventing a tenant field or overwrite assignment and notes.

Version-specific logical identity is separate from delivery identity. v1 and v2 do not merge into one alert. An internal delivery UUID identifies one admission attempt across its internal retries; a new client submission receives a new UUID. Walk the pipeline

Choose a scenario and advance one boundary at a time. Offset n is a synthetic input position. The final downstream order is illustrative; correlation and indexing use independent groups.

    The two commits

    1. Commit PostgreSQL: apply the source mutation, history, maintenance proof and immutable source result together. The result retains the input digest, original topic/partition/offset and exact changed-event bytes.
    2. Commit Kafka: publish changed events and the consumed input offset plus one in a single Kafka transaction. Downstream groups use read_committed.

    There is no atomic transaction across these two systems. A crash between them is expected. Replaying the original input retrieves the original immutable bytes rather than reapplying the alert or recomputing the event from newer state. If a person assigned or resolved the alert meanwhile, the replay must not undo that command.

    Ordering, producer fencing and duplicate coordinates

    Received records are partitioned by the canonical tenant/application/key tuple and processed in Kafka append order, not UTC timestamp order. Changed records are keyed by tenant. Stable transactional producer IDs include environment, protocol and input partition. Assignment initializes/fences the previous producer before reading committed offsets. An uncertain transaction requires rejoining and settling the producer state; blindly republishing from a stale assignment can corrupt the protocol.

    The same delivery UUID at a different coordinate advances without applying a second semantic mutation or emitting another semantic changed event. Conflicting content under an existing UUID is a protocol fault. Partition counts are not casually changed on a running pipeline; the cutover contract applies.

    What the sender response actually guarantees

    A per-member 202 means validation and broker-confirmed acceptance, not PostgreSQL application, correlation completion or search visibility. Kafka retention can lose an accepted record before processing. Admission does not consult PostgreSQL for backlog or authority availability.

    Valid batch members publish individually, preserving result indices. All accepted gives 202; mixed results can give 207; all validation failures give 422; when valid publications all fail, 503 takes precedence. Three unconfirmed internal publish attempts return a retryable error, but publication may still have occurred. Do not describe 503 as proof that nothing entered Kafka.

    Some business conflicts are discovered after 202 and are terminal internal outcomes with retained diagnostics. Transient failures keep the input position for retry. Unknown internal proof and retention gaps require explicit diagnosis and fencing; “skip this record” is not a generic recovery procedure.

    03 · Business invariants

    Keep lifecycle, ownership and suppression separate

    An alert is a continuing logical record, not one delivery. It can contain multiple firing occurrences and many source/history events. Assignment, notes and incident membership are management state. The source supplies its permitted fields; it does not control arbitrary management values.

    The raw lifecycle is firing or resolved. Current display status is derived: firing without an assignee is Firing, firing with an assignee is Acknowledged, and resolved remains Resolved regardless of assignment. There is no separate acknowledgement command. New occurrences clear alert assignment; incident reopening instead preserves an eligible assignee.

    Alert state playground

    Start with one firing alert in occurrence 1. Try assigning it, resolving it and firing it again. Then introduce a qualifying maintenance entry, end the window and send a source repeat. Source repeat resends the last firing/suspended payload as a new delivery, so it can reopen a manually resolved alert. The lab assumes a maintenance predicate unaffected by manual status/assignment changes; real commands that make its condition false can close that cause. These events illustrate selected domain rules, not a full evaluator.

    Inspect the simulated event history

      Suppression is a union of independent causes

      v2 source suspension and maintenance causes can overlap. Effective suppression remains while any cause is open. Suppressed alerts continue to be ingested and stored; ordinary feeds/counts and automatic correlation exclude them. Manual incident links may still include them.

      A maintenance window is one-time and does not backfill existing matching alerts. Qualifying new arrivals/transitions create coverage. Under the current release scope, the end/disable/delete boundary stops new coverage but does not run a timer sweep over existing alerts. The next source input received at or after the boundary can close that cause, including an unchanged repeat. A delayed input received inside the window stays covered even if processed later. Reading, indexing or editing a note does not release expired coverage.

      Incidents coordinate work; correlation supplies evidence

      An incident has its own Open/Investigating/Resolved lifecycle, immutable severity, assignment, notes and cycles. One alert can have at most one active incident owner; historical resolved relationships can remain. Resolving an incident releases active ownership but does not resolve alerts. Alert resolution does not close the incident. Link/move operations must preserve atomic membership and lock ordering.

      A correlation rule requires fresh eligible evidence for all named conditions inside its window and group. A single alert can satisfy multiple conditions. Once an incident is active, an eligible alert matching any condition can be added. Earlier-created qualifying rules win competing automatic claims. Correlation rechecks current state because the alert may have changed after the consumed event.

      Why a matching alert may not create an incident

      It may be suppressed, resolved, already owned, outside a rule epoch or time boundary, or lack a genuine qualifying transition. Repeated identical deliveries do not refresh evidence. Creating/enabling a rule does not backfill retained matches. Manual edits do not manufacture source evidence; manual resolve clears active evidence atomically. In the Kafka-first rule context, assignee_id is excluded from conditions and grouping even though it remains available to feed/maintenance queries.

      Changing grouping prevents old-group incidents receiving additions through the new grouping. Disabling/deleting a rule or suppressing an alert does not erase existing incident links. Test tools report candidate matching, not proof that a historical window was satisfied.

      Shared views are references, not snapshots of data

      A preset stores name, CEL, sort and columns. Quick views, free-text search and suppression inclusion are transient. Dashboard panels reference the preset's current saved query; copies retain those references. Counts represent distinct logical alerts, exclude suppressed records and include resolved records unless CEL excludes them. Panel thresholds only change presentation.

      Prevent dangling references transactionally: a referenced preset cannot be deleted while a current dashboard panel uses it. Configuration history reuse creates a new validated revision instead of moving history backward. Deferred physical cleanup does not extend read-time access windows or revive previously retired content.

      04 · Request paths

      Design for concurrency and visible lag

      Trace a human command

      1. The browser sends its authenticated session, CSRF protection, a command identity and the observed revision required by that operation.
      2. The API reauthorizes the tenant and nested resources. A repeated command identity with the same scoped payload can return its recorded result; reuse with different content is a conflict.
      3. The transaction obtains the required coordination/domain locks, rechecks revision and eligibility, and changes state/history/receipt together.
      4. The API returns authoritative state. Best-effort search notification and live invalidation follow their contracts; failure to send a hint does not roll back the committed business command.
      5. Other views refetch and search converges. A queued source update can legitimately change the record after the manual command.

      Expected revision prevents lost updates; command identity prevents duplicate execution. They solve different problems. After an ambiguous network timeout, preserve the original identity/body and use the command recovery flow. After a revision conflict, keep the user's draft, show/review the latest state, then make an intentional new decision. A replayed receipt is not proof that its old revision is still current.

      Locks and shared transaction mechanics

      Read the affected operation's exact lock order before changing it. Authorization guards precede domain locks. Common paths coordinate the tenant, lock relevant catalog/context/incident state and then the complete sorted alert/evidence scope. Reference changes have their own documented configuration guard. Do not create an inverted path by adding one late lock. Compile bounded CEL work before acquiring long-lived domain locks, and keep remote calls outside SQL transactions.

      The shared helper supplies coordinator clock checks, scoped command receipts and revision checking. It does not replace the operation's required invariants. Use transactional/concurrency tests that prove two competing requests cannot both commit an invalid result.

      Trace a search

      The API authorizes the tenant, compiles supported CEL and combines it with transient text and suppression policy. Elasticsearch searches current alert/current-note projections; PostgreSQL remains the source for detail/history and authorization. This is not a historical search engine or a full event-sourcing system.

      Feed traversal uses a bounded point-in-time snapshot; query/sort/context changes restart it. Relative now() is captured for the query rather than evaluated independently for each row. Exact counts and row results must share the correct effective filter/context. Never replace a failed search with zero or silently broaden invalid CEL to true.

      The native CEL compiler, supported catalog, bounded execution and Elasticsearch translator must agree. New operators or fields can affect feeds, maintenance and correlation differently. Use the actual compiler and parity checks; a mock that duplicates your translator's assumptions does not establish semantic equivalence.

      Projection and live updates recover differently

      The indexer uses Kafka hints plus bounded PostgreSQL reconciliation, external versions, tenant scan leases and refresh-visible proof. After a completed full pass, ordinary scans can use projection-version deltas; periodic full audits repair externally missing unchanged documents. Equal-version content conflicts or foreign higher external versions require operational repair. Failed indexing cannot advance its covered searchable watermark; a failed periodic audit does not block ordinary delta progress. A large note collection can exceed the configured projection document allocation: retain authority, report the failure and never truncate notes to pretend indexing succeeded.

      The Product API owns live publishing, Redis subscription, SSE and PostgreSQL generation reconciliation. There is no separate live worker. Losing Redis can delay hints, but connected clients reconcile and refetch. The browser must reject late responses for an old tenant, query, revision or draft and clear protected state when access is lost.
